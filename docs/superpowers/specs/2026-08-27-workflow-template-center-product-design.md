# Workflow 模板中心产品方案

状态：核心决策已确认，待技术拆解

## 1. 结论摘要

Workflow 模板应作为现有 Workflow 模块中的一种内容形态，由现有 Workflow 草稿转换生成；它与租户 Workflow 使用同一套编辑器和节点能力，但拥有独立的数据生命周期。

首期建议采用以下产品定义：

1. 模板不是新的一级页面，而是嵌入「我的 Workflow」列表下方的模板区块；用户可以在当前页面快速浏览推荐模板。
2. 点击「查看更多」打开模板弹窗，在弹窗内按页浏览全部模板；模板详情也在弹窗内完成只读预览。
3. 模板详情使用现有 Workflow 画布进行只读预览，允许平移、缩放、查看节点配置，不允许任何编辑或试运行操作。
4. 「应用模板」一次点击立即创建一份租户自己的可编辑 Workflow Draft，并进入编辑器。
5. 应用不会发布、启用或覆盖现有 Workflow；发布仍经过现有校验和审核流程。
6. 应用后的 Workflow 与源模板脱钩。模板后续升级、下线或归档，不改变已经创建的 Workflow。
7. 模板中不得保存托管账号、成员、标签、人群、模型、素材等租户资源 ID。这些依赖以“待配置项”呈现，应用后由用户完成选择。
8. 首期只允许平台运营维护公共模板，不开放租户把自己的 Workflow 投稿为公共模板，也不开放企业私有模板。

这里的“一键应用”表示“一键获得可编辑的完整流程骨架”，不表示“一键发布并开始运行”。

## 1.1 落地重点

本方案真正需要落地的是两个相互独立的模块：

| 模块 | 主要使用者 | 交付结果 |
| --- | --- | --- |
| 模板管理与发布 | 平台运营 | 一个经过校验、可被租户应用的不可变 Template Version |
| 模板展示与应用 | 租户 owner/admin | 在 Workflow 列表下方浏览模板，在弹窗中查看并一键生成 Draft |

模板管理模块负责“内容正确、资源安全、版本可追溯”；模板展示模块负责“发现成本低、查看足够、应用路径短”。两者通过已发布 Template Version 连接，不共享可变 Draft。这里的“独立”只指数据生命周期、权限和入口，不指另一套后台或另一套编辑器。

最小可落地能力是现有 Workflow 编辑器中的「转换为模板」：从一个可编辑 Draft 生成一个 Template Draft。转换不修改源 Workflow，也不自动发布；发布仍是后续的独立确认动作。

## 2. 现状与设计约束

当前 Workflow 已具备以下能力：

- Workflow Type 在创建时确定，并固定主体类型和可用能力。当前可用类型是 ChatAI SOP 和 WeCom SOP。
- Workflow Definition 持有可变 Draft，发布后生成不可变 Workflow Revision。
- 编辑器已有 read-only 和 version-preview 模式，能够阻止图编辑，同时保留画布浏览能力。
- Draft 可包含未完成配置；发布时由前后端共同校验图结构、节点配置、类型策略和 Runtime Support。
- Start、标签、受众、模型、素材等配置可能引用租户自己的业务资源。
- 创建 Workflow 已有 `clientRequestId` 幂等语义，并受权限、Product Entitlement 和租户 Workflow 数量上限约束。
- 当前 Workflow 模块只允许 owner/admin 访问。

因此，模板不能直接复用 Workflow Revision，也不能把另一个租户的 Draft 原样复制给用户。模板需要独立的版本、发布和资源占位语义；但这些语义应建立在现有 Workflow 编辑器和节点契约之上，而不是复制一套实现。模板的来源是 Workflow Draft 的一次转换快照，不是对源 Workflow 的持续同步。

## 3. 产品目标与非目标

### 3.1 产品目标

- 降低用户从空白画布开始设计 Workflow 的认知成本。
- 让用户在应用前看清完整路径、节点作用和需要准备的资源。
- 将常见业务实践沉淀为可治理、可迭代、可度量的平台内容。
- 保持现有 Draft、发布审核、Revision 和 Runtime 安全边界不变。
- 让模板升级不影响已经运行或正在编辑的租户 Workflow。

### 3.2 首期非目标

- 不做模板自动发布或自动启用。
- 不把模板变成持续同步的“母版”。
- 不自动按名称匹配租户标签、人群、模型或素材。
- 不允许租户编辑公共模板源内容。
- 不开放租户投稿、分享链接、收费模板或模板交易。
- 不支持跨 Workflow Type 转换模板。
- 不承诺应用后无需配置即可发布。

## 4. 领域模型

### 4.1 核心术语

**Workflow Template**

由平台维护的可复用 Workflow 起点。它固定一个 Workflow Type，包含用户可见说明、可移植的流程草稿和应用前置条件。它不是 Workflow Definition，不能被启用或产生 Workflow Run。

**Template Version**

Workflow Template 的不可变发布快照。用户每次查看和应用的都是一个明确版本。发布后的内容、流程和配置项不能原地修改。

**Template Configuration Item**

模板应用后必须或建议由租户完成的配置，例如选择托管账号、添加方式、标签、人群、模型或客户字段。配置项指向稳定的节点和业务字段，不保存任何租户资源 ID。

**Template Application**

使用某个 Template Version 创建一个新 Workflow Definition 的动作。结果是普通 Workflow Draft，后续生命周期完全遵循现有 Workflow 规则。

### 4.2 核心不变量

- 一个 Workflow Template 只属于一个 Workflow Type。
- 一个已发布 Template Version 永远不可变。
- Template Application 只能创建新 Workflow，不能覆盖或合并到已有 Workflow。
- Template Application 不创建 Workflow Revision，不提交审核，不启用 Workflow。
- 应用时使用用户正在查看的确切 Template Version。
- 模板包含的节点必须全部属于对应 Workflow Capability Profile，并具备当前 Workflow Runtime Support。
- 模板节点 ID 在复制后保持不变，以保留边、变量选择器和分支出口引用；节点 ID 只要求在单个 Workflow 内稳定。
- 模板更新或下线不改变已经应用的 Workflow。
- 模板不得包含租户身份、租户业务资源 ID、密钥、真实客户数据或真实运行数据。

## 5. 信息架构

### 5.1 Workflow 列表下方的模板区块

模板区块位于现有 Workflow 列表之后，作为创建 Workflow 的辅助入口，不改变当前列表的数据概览、状态筛选、搜索和分页。

区块标题建议为「推荐模板」，右侧提供「查看更多」。首屏只展示运营精选的 4 个模板，按运营排序值倒序排列；数量不足 4 个时按实际数量展示。每张卡片展示：

- 真实流程拓扑缩略图。
- 模板名称和两行以内的结果描述。
- Workflow Type。
- 节点数。
- 必配项数量。
- 模板标签。

点击卡片打开模板详情弹窗；点击「查看更多」打开模板浏览弹窗。区块本身不提供独立分页，也不在卡片上直接应用。

区块放在 Workflow 列表分页之后，作为列表页的底部内容，不插入表格行，也不跟随某个 Workflow。这样用户完成列表浏览后自然进入“从模板开始”的下一条路径；列表请求失败时不阻塞模板区块请求。

推荐区块只请求一页 `limit=4` 的精选模板，不读取全部模板。模板区块与模板浏览弹窗共用同一张卡片适配器，确保标题、描述、Workflow Type、标签和必配项数量的含义一致。

Workflow 列表为空时，模板区块仍然显示，并与「空白创建」并列承担首个行动入口：用户可以选择空白创建，也可以从推荐模板开始。

### 5.2 模板浏览弹窗

「查看更多」打开模板浏览弹窗，而不是跳转到新的模板中心页面。弹窗负责全部模板的搜索、筛选和分页浏览：

- 名称搜索，仅匹配模板名称。
- Workflow Type 筛选：全部、ChatAI SOP、WeCom SOP。
- 标签筛选：按标签维度展示，支持同一维度多选，筛选条件之间使用 AND 匹配。
- 默认按运营排序值倒序，再按 Template ID 倒序稳定排序。
- 每页展示 8 个模板，底部使用上一页、页码和下一页；具体页大小可按弹窗高度调整，但接口 `pageSize` 必须有明确上限。
- 搜索只匹配模板名称；筛选条件变化时回到第一页并清空旧列表，保持 loading、empty、error 三态区分。
- 关闭弹窗后返回 Workflow 列表原滚动位置；打开弹窗时默认回到上次浏览页仅在同一次页面会话内有效。

弹窗列表视图建议采用“顶部筛选 + 中部卡片网格 + 底部分页”的固定结构。分页使用明确的上一页、当前页和下一页，不使用无限滚动，避免用户失去模板位置，也便于埋点统计每一页的曝光。

弹窗列表只负责选型，不提供直接应用按钮。用户必须先进入详情视图，确认流程和待配置资源后才能应用。

模板浏览弹窗的卡片与下方推荐模板区块保持同一张卡片语义，避免用户在两个入口看到不同字段或不同操作。

### 5.3 模板详情弹窗视图

点击模板卡片后，浏览弹窗切换到同一弹窗内的模板详情视图，不再打开独立路由或全屏页面。详情视图提供返回按钮，返回后保留浏览弹窗的筛选、页码和滚动位置：

```text
┌──────────────────────────────────────────────────────────────┐
│ 返回  模板名称  Workflow Type              [应用模板]       │
├──────────────┬───────────────────────────────┬───────────────┤
│ 模板概览     │                               │ 节点详情      │
│ 适用场景     │        只读 Workflow 画布      │ 点击节点后显示 │
│ 流程说明     │                               │ 只读配置摘要   │
│ 使用前准备   │                               │               │
│ 配置项 3     │                               │               │
└──────────────┴───────────────────────────────┴───────────────┘
```

模板概览区展示：

- 模板要解决的业务场景。
- 触发条件的业务描述。
- 流程步骤摘要。
- 使用前准备和必配项。
- 节点数与当前版本发布时间。

只读画布允许：

- 平移、缩放、适应画布。
- 选中节点。
- 查看节点的只读配置摘要。
- 查看分支路径、消息内容、等待时长和变量引用。

只读画布禁止：

- 拖动节点、增删节点、连线或自动布局。
- 修改节点配置、复制粘贴、撤销重做。
- 试运行 AI 节点。
- 保存、提交审核、发布或启用。
- 通过键盘快捷键触发任何写操作。

桌面端详情视图使用弹窗内部的三栏布局；移动端将概览和节点详情收进抽屉，画布保持主要视图。「应用模板」固定在详情视图顶部操作区。关闭弹窗即退出模板浏览，不影响 Workflow 列表。

详情视图加载失败时保留弹窗壳和返回按钮，提供重试；应用成功后才关闭模板弹窗并跳转到新 Workflow 编辑器。应用失败时停留在详情视图，不丢失用户当前浏览位置。

### 5.4 一键应用

用户在模板详情点击「应用模板」后，不再弹出名称或资源配置表单。系统执行一次原子创建：

1. 校验用户仍有 Workflow 权限。
2. 校验 Template Version 仍可应用。
3. 校验租户拥有该 Workflow Type 的 Product Entitlement。
4. 校验租户未达到 Workflow Definition 数量上限。
5. 服务端读取模板版本并再次完成 Draft Schema、Workflow Type、节点支持和资源中立性校验。
6. 创建名称等于模板名称的新 Workflow Definition，并记录模板来源。
7. 返回新 Workflow，前端跳转到标准 Workflow 编辑器。

按钮请求中进入 loading 并防止重复点击。请求携带 `clientRequestId`，网络重试或双击只能得到同一个 Workflow。

名称允许重复，因此不在应用前增加命名步骤。用户可在编辑器中按现有能力重命名。

应用成功后：

- 进入新 Workflow 的编辑模式。
- 自动打开「配置清单」。
- 顶部短暂显示「已从“模板名称”创建」。
- 不自动保存模板以外的新修改，不自动提交审核。

应用失败时不产生半成品 Workflow。已达到数量上限、无权限或无 Product Entitlement 时展示可行动的具体原因；普通网络或服务错误使用统一失败提示。

### 5.5 应用后的配置清单

配置清单不是新的校验体系，而是现有发布校验的模板化导航视图。它按流程执行顺序列出 Template Configuration Item：

- 必须配置：未完成时阻止发布。
- 建议确认：有通用默认值，但用户应检查。
- 已完成：当前 Draft 已满足要求。

点击配置项选中对应节点并打开现有节点设置面板。配置完成后清单即时更新。所有项完成后，用户仍通过现有「检查 -> 提交审核 -> 发布 -> 启用」路径完成上线。

应用时将配置清单复制为新 Workflow 的来源上下文快照。清单只属于应用后的 Workflow Draft，不持续读取模板，也不会因模板更新而变化。

## 6. 模板内容设计

### 6.1 可复制内容

下列内容可以进入 Template Version：

- 节点和边。
- 节点位置和默认 viewport。
- 等待时长、比例、分支逻辑等通用流程参数。
- 通用消息文本、Prompt、字段收集说明等平台编写内容。
- 变量选择器和节点间引用。
- Workflow Type。
- 模板名称、标签、结果描述、流程说明和前置条件。

### 6.2 必须留空的租户内容

至少包括：

- ChatAI Seat 和 WeCom Member。
- 添加方式、活动来源和触发标签。
- 标签动作和标签查询使用的标签。
- 人群组。
- 租户模型。
- 客户自定义字段。
- 素材库附件和其它租户素材。
- 将来新增的任何租户业务资源。

模板可以保留资源的业务意图，例如“选择欢迎活动来源”“选择高意向标签”，但不能保存实际资源 ID，也不能按资源名称自动绑定。

### 6.3 Template Configuration Item

配置项建议使用结构化定义，不允许运营人员手写任意 JSON Path：

```ts
type TemplateConfigurationItem =
  | {
      bindingKey: string;
      id: string;
      kind: "resource";
      nodeId: string;
      requirement: "required" | "recommended";
      resourceKind:
        | "managed-account"
        | "friend-add-way"
        | "tag"
        | "audience-group"
        | "model"
        | "customer-field"
        | "material";
      title: string;
    }
  | {
      fieldKey: string;
      id: string;
      kind: "review";
      nodeId: string;
      requirement: "required" | "recommended";
      title: string;
    };
```

`bindingKey` 和 `fieldKey` 都是节点契约注册的稳定 Key，不是运营人员手写的 JSON Path。资源配置项定位必须选择的租户资源；确认项提示用户检查模板自带的消息、Prompt、等待时长等通用默认值。这样新增节点资源类型时，资源清理、模板发布校验、应用后清单和测试都集中在同一模块，而不是散落在模板页面和后端路由。

## 7. 模板管理

### 7.1 管理范围

首期模板只由拥有 `workflow_template_manage` 权限的平台运营维护，不出现在租户工作台导航。租户 owner/admin 只能查看和应用，不能修改公共模板。

模板不建设第二套编辑器。运营从现有 Workflow 草稿执行「转换为模板」，模板管理入口只负责查看转换结果、填写模板元数据、执行检查、预览和发布。

`workflow_template_manage` 由后端基于写死的 `uid + sub_user_id` 身份白名单判断，不读取环境变量，也不接受前端传入的权限结果。前端只根据当前会话隐藏或展示入口，转换、发布、下线和归档接口必须再次执行后端鉴权。MVP 使用一个权限覆盖全部模板管理动作，未来如有需要再拆分编辑和发布权限。

所有变更记录操作人和时间。模板管理操作只允许产生全平台公共模板，不产生租户私有模板。

### 7.2 生命周期

模板目录状态和转换生成的 Template Draft 是两个独立维度：

```text
Template Draft --发布--> 不可变 Template Version

未发布 --首次发布--> 已上线 <--> 已下线 --> 已归档
```

- Template Draft：由某个 Workflow Draft 转换生成，只在模板管理入口可见，可补充元数据和配置项，不影响当前线上版本。
- 未发布：尚无任何线上版本。
- 已上线：当前发布版本出现在模板中心，可以查看和应用。
- 已下线：用户目录立即隐藏并禁止新增应用，已有 Workflow 不受影响；允许从新的 Workflow Draft 重新转换后重新发布。
- 已归档：永久停止新增应用，只保留审计和历史版本，不再编辑。

已上线模板可以同时拥有新的 Template Draft；用户继续看到当前发布版本。再次发布会冻结新的不可变 Template Version 并切换当前线上版本，不原地修改旧版本。

紧急撤回时可以单独将某个 Template Version 标记为 revoked。已经应用的 Workflow 不自动修改；运营需要通过独立公告或风险处置流程联系受影响租户。

### 7.3 管理列表

管理列表至少包含：

- 模板名称。
- Workflow Type。
- 模板标签。
- 当前发布版本。
- 状态。
- 最近更新时间和操作人。
- 累计应用次数。

支持按名称搜索、Workflow Type、状态和标签筛选。支持从 Workflow Draft 转换、补充元数据、预览、发布、下线和归档。

管理列表的主操作顺序固定为「查看转换结果 -> 补充元数据 -> 预览 -> 提交发布」。已发布版本不能直接编辑；需要更新内容时，从新的 Workflow Draft 重新执行「转换为模板」。当前线上版本、Template Draft 和历史版本在列表中分栏显示，避免运营误以为修改会立即影响租户侧模板。

### 7.4 从 Workflow Draft 转换为模板

模板的唯一内容生产入口是现有 Workflow 编辑器中的「转换为模板」动作，不另做模板画布。

转换流程：

1. 用户在可编辑的 Workflow Draft 中完成通用流程。
2. 拥有 `workflow_template_manage` 权限的用户点击「转换为模板」。普通租户用户默认不显示该操作。
3. 服务端按指定 `draftVersion` 或 Draft semantic hash 读取草稿，避免把用户未保存的前端状态当成模板来源。
4. 服务端复制 Draft，移除租户资源 ID，并自动生成待配置项草稿。
5. 返回转换报告：已转换字段、需要人工确认的字段、无法转换的阻断项。
6. 用户补充模板元数据和配置项说明，生成一个 Template Draft。
7. 进入模板管理列表执行检查、预览和发布。

转换不会修改源 Workflow，不会创建 Workflow Revision，不会改变源 Workflow 的运行状态，也不会建立后续同步关系。源 Workflow 只是模板内容的来源快照。

模板内容修改也沿用这个原则：先修改源 Workflow 的最新已保存 Draft，再重新执行「转换为模板」，生成新的 Template Draft。首期不允许在模板侧独立编辑图，避免出现两份画布实现和两套节点维护链路。

现有 Workflow 编辑器、节点注册表、节点 Definition、Draft Schema、连接规则、布局和校验模块全部复用；新增节点只需维护现有 Workflow 节点能力，转换逻辑通过节点契约读取资源字段，不维护第二份节点目录。

转换后的模板只需要补充两类信息：

1. **模板元数据**：模板名称、标签、结果描述、流程说明、使用前准备、排序。
2. **模板配置项**：对已被清理的租户资源字段声明“必须配置”或“建议确认”，填写用户能理解的标题和引导说明。

典型映射示例：

| 节点字段 | 模板中的处理 | 应用后的用户动作 |
| --- | --- | --- |
| Start 的托管账号/企微成员 | 留空并声明 `managed-account` 配置项 | 选择可用账号或成员 |
| Start 的添加方式/活动来源 | 留空并声明 `friend-add-way` 配置项 | 选择来源 |
| Tag / Tag Query 的标签 | 留空并声明 `tag` 配置项 | 选择标签 |
| LLM 的模型 | 留空并声明 `model` 配置项 | 选择租户模型 |
| Message 的素材附件 | 移除租户素材引用，保留文案或声明 `material` 配置项 | 选择素材或重新上传 |
| Customer Update 的字段 | 保留字段语义，声明 `customer-field` 配置项 | 选择租户客户字段 |

模板作者可以保留通用默认值，但不能在转换结果中保留任何真实租户资源。资源字段由转换器统一替换为占位项；同一个字段在租户 Workflow 编辑上下文中仍由现有资源选择器负责绑定。

不建议通过 SQL 直接编辑 Draft JSON，也不建议长期用代码常量维护模板。Workflow 图和节点配置复杂，必须经过同一套 Schema、类型策略和发布校验。

### 7.5 模板发布门槛

发布模板时必须全部满足：

- 基础信息完整，名称和描述符合长度限制。
- 图结构可发布：唯一 Start/End、可达、无环、分支出口完整。
- 所有节点属于 Workflow Type 的 Capability Profile。
- 所有节点均具备当前 Runtime Support；placeholder 或仅 draft-ready 节点不能进入公共模板。
- 通用配置完整，所有缺失的租户资源配置都被明确的 Template Configuration Item 覆盖。
- Draft 不包含租户资源 ID、用户身份、客户数据、密钥或运行数据。
- Draft 能被当前节点契约正常 hydrate；为所有资源配置项注入仅用于校验、不会持久化的合法测试值后，能够通过同一后端 compiler。
- 只读详情、缩略图、配置清单和应用后的 Draft 均通过预览验收。

模板发布校验不能复用普通 Workflow 的“所有执行配置必须完成”作为唯一结论，因为模板有意保留租户资源空位；但除已声明配置项以外的错误必须阻止发布。

模板发布采用两步确认：

1. **自动检查**：系统生成检查结果，包含阻断项、警告项和统计信息；阻断项必须修复，警告项必须由发布人确认。
2. **发布确认**：发布人确认当前 Template Draft 将生成新的不可变 Template Version，并切换为当前线上版本。发布动作原子完成，不能出现“版本已生成但目录仍指向旧版本”的中间状态。

发布后的版本立即用于推荐区块和浏览弹窗；旧版本继续保留在历史记录中，但不再出现在租户侧目录。若需回滚，回滚动作是把某个历史版本重新发布为新的版本号，不修改旧快照。

建议发布结果明确展示：版本号、发布人、发布时间、节点数、配置项数量、阻断检查数和警告检查数。这样运营可以判断“发布成功”与“可被用户顺利应用”不是同一件事。

## 8. 数据与接口边界

### 8.1 推荐数据模型

**Template 主记录**

- `id`
- `status`
- `current_published_version`
- `sort`
- `create_time` / `update_time`
- `created_by` / `updated_by`，记录内部运营身份

**Template Version 不可变快照**

- `template_id` / `version`
- `workflow_type`
- 名称、描述、标签、流程说明、前置条件
- `draft_schema_version`
- `draft_json`
- `configuration_items_json`
- `semantic_hash`
- `published_by` / `publish_time`
- `availability`，用于紧急 revoke

**Template Draft 转换来源**

- `source_workflow_id`
- `source_workflow_draft_version`
- `source_workflow_semantic_hash`
- `conversion_report_json`

这些字段只用于审计和问题定位，不表示模板会跟随源 Workflow 自动更新。

**Workflow 应用**

应用模板时直接按模板草稿创建普通 Workflow Definition，不在营销 Workflow 定义表中保存模板来源或配置快照。模板与应用后的 Workflow 相互独立，后续编辑和发布不产生持续关联。

### 8.2 用户侧接口

建议保持三个小接口：

```text
GET  /api/server/workflow-templates
GET  /api/server/workflow-templates/:templateId
POST /api/server/workflow-templates/:templateId/applications
```

转换动作属于现有 Workflow 编辑器的受保护写操作，建议由当前 Workflow 路由承载：

```text
POST /api/server/workflows/:workflowId/template-conversions
```

请求携带 `expectedDraftVersion` 或 `expectedDraftSemanticHash`。服务端返回 Template Draft、配置项草稿和转换报告；转换失败时不创建半成品 Template Draft。

模板列表接口支持两种调用场景，但保持同一套排序和卡片字段：

```text
GET /api/server/workflow-templates?surface=workflow-list&featured=true&limit=4
GET /api/server/workflow-templates?surface=workflow-list&page=1&limit=8&workflowType=...&tags=...
GET /api/server/workflow-templates/:templateId
POST /api/server/workflow-templates/:templateId/applications
```

推荐区块使用 `featured=true&limit=4`；查看更多弹窗使用筛选条件和页码分页。接口返回总数，前端首次加载即可确定全部可达页码，并支持直接跳转到目标页，不要求用户逐页翻阅。

应用请求包含用户查看的 Template Version 和 `clientRequestId`。服务端隐藏模板读取、版本校验、资源中立校验、Workflow 创建和来源记录等实现细节。

不建议让客户端执行“先创建空白 Workflow，再 PUT 模板 Draft”的两步操作。该方案会产生半成品、增加并发窗口，并让客户端承担不应信任的模板复制逻辑。

也不建议把任意 `draft` 加入普通 Workflow Create Request。模板 Draft 必须来自服务端已发布版本，不能接受客户端提交的模板内容作为可信来源。

### 8.3 查询规模

- 模板列表使用数据库分页，不一次性读取所有模板；单页查询数量固定，页码上限为 1000。
- 列表接口直接返回卡片需要的元数据、节点数、必配项数和缩略图地址，不逐模板补请求。
- 详情只发一个模板请求，不在预览阶段逐项请求租户资源。
- 应用后配置面板沿用现有资源接口；同类资源按页面或面板一次加载，不按配置项 N 次请求。

## 9. 关键状态与异常

### 9.1 模板区块与浏览弹窗

- loading：显示稳定尺寸的骨架或 Spinner，不同时显示空态。
- empty：当前筛选无结果时显示「暂无数据」，并允许清除筛选。
- error：保留筛选条件，提供重试。
- 模板在推荐区块或浏览弹窗中下线：详情请求返回不存在或已下线，关闭详情视图并刷新当前弹窗页。
- 弹窗分页请求失败：保留当前页和筛选条件，显示重试入口，不回退到 Workflow 列表。

### 9.2 应用

- 重复点击或网络重试：由同一个 `clientRequestId` 返回同一 Workflow。
- 模板版本已 revoked：禁止应用并刷新详情。
- 模板已下线或归档：即使详情页仍打开，也禁止新增应用。
- 模板已发布新版本：默认仍应用用户正在查看且未 revoked 的版本，保证“所见即所得”。
- 无 Product Entitlement：禁止创建并提示当前类型不可用。
- 达到 Workflow 数量上限：禁止创建并引导清理不再使用的 Workflow。
- 节点契约已不兼容：禁止应用，模板自动从公共列表降级为不可用并通知运营处理。
- 普通服务失败：不留下 Definition，使用统一错误提示。

## 10. 初始模板建议

首期控制在 5 至 8 个高完成度模板。候选模板必须以发布当时真实 Runtime Support 为准，下面只定义业务方向：

| 模板 | Workflow Type | 业务路径 | 典型必配项 |
| --- | --- | --- | --- |
| 新客欢迎 | ChatAI SOP | 新增好友 -> 发送欢迎消息 -> 结束 | 托管账号、添加方式 |
| 高意向识别与人工接待 | ChatAI SOP | 收到消息 -> AI 意图识别 -> 分支 -> 转人工/结束 | 托管账号 |
| 客户信息收集与更新 | ChatAI SOP | 收到消息 -> AI 收集 -> 更新客户资料 -> 结束 | 托管账号、客户字段 |
| 新增好友自动打标 | WeCom SOP | 新增好友 -> 添加标签 -> 结束 | 企微成员、添加方式、标签 |
| 新客 A/B 分组 | WeCom SOP | 新增好友 -> 比例分流 -> 分别打标 -> 结束 | 企微成员、添加方式、标签 |

不应为了凑模板数量使用 placeholder 节点、虚构触发能力或尚未接通的业务资源。

## 11. 指标与埋点

### 11.1 核心指标

北极星指标：模板应用后 7 日内成功发布的 Workflow 数量及比例。

关键漏斗：

```text
Workflow 列表下方模板区块曝光
-> 点击查看更多或推荐模板卡片
-> 在弹窗中打开模板详情
-> 点击应用模板
-> 完成必配项
-> 提交审核
-> 发布
-> 首次成功运行
```

### 11.2 效率与质量指标

- 模板创建到首次提交审核的中位时长，对比空白创建。
- 模板应用后 24 小时和 7 日内发布率。
- 各模板详情到应用转化率。
- 应用后未编辑、未删除、未提交审核的滞留率。
- 应用接口错误率和幂等重放率。
- 每个模板应用后最常见的发布校验错误。
- 应用后 Workflow 前 7 日运行失败率，对比空白创建。
- 模板版本更新前后的发布率和运行质量变化。

模板使用次数不能作为唯一排序依据，避免头部模板永久占据曝光。默认仍由运营排序，使用数据只作为运营决策输入。

## 12. 分期建议

### Phase 1：可用闭环

- Workflow 列表下方推荐模板区块。
- 模板浏览弹窗、分页、筛选、搜索和弹窗内只读详情。
- 平台公共模板管理、不可变版本、发布、下线和归档。
- 一键创建独立 Workflow Draft。
- 配置清单。
- 来源记录和完整漏斗埋点。
- 5 至 8 个经过发布验收的初始模板。

### Phase 2：运营效率

- 模板版本差异预览和历史版本恢复。
- 模板兼容性巡检和异常自动下线。
- 基于数据的排序建议，不自动替代运营排序。
- 配置项默认值和更细的引导文案。
- 模板效果看板。

### Phase 3：受控扩展

- 企业私有模板。
- 将租户 Workflow 转为私有模板时的资源脱敏检查。
- 企业内分享和模板权限。

公共模板投稿、跨租户分享和模板交易只有在内容审核、归属、脱敏和责任机制成熟后再评估。

## 13. 多轮方案论证

### 第一轮：模板是否直接复用 Workflow Definition

候选方案：

- 把平台模板建成 `uid = 0` 的特殊 Workflow Definition。
- 给每个租户复制一份预置 Workflow。
- 建立独立 Workflow Template 和 Template Version。

结论：选择独立模型。

原因：Workflow Definition 是租户控制面对象，具备 Draft、Review、Revision、Runtime Status 和 Run 关系；模板没有运行生命周期。用 `uid = 0` 复用会把权限、发布、运行和模板治理绑在一起，后续很难安全演进。预先复制则制造大量无人使用的数据，并无法解决模板更新。

### 第二轮：“一键应用”是否直接发布

候选方案：

- 应用后直接发布并启用。
- 应用前先完成一套配置向导，再创建 Workflow。
- 一键创建 Draft，进入编辑器完成配置。

结论：选择一键创建 Draft。

原因：直接发布会绕过租户资源选择、发布校验和审核；前置向导会复制节点面板能力，且配置失败前用户看不到真实编辑环境。创建 Draft 是可逆操作，复用现有编辑、校验和审核路径，也符合用户对“一键获得模板”的预期。

### 第三轮：租户资源如何处理

候选方案：

- 把模板作者选择的资源 ID 原样复制。
- 按资源名称在目标租户自动匹配。
- 清空租户资源，通过结构化配置项引导用户选择。

结论：选择结构化配置项。

原因：跨租户 ID 没有意义且存在数据泄露风险；名称匹配会把同名资源误绑定到真实执行路径。明确留空虽然要求用户补充配置，但结果可解释、可校验，不会产生静默错误。未来可以做候选推荐，但默认不能自动绑定。

### 第四轮：应用后的 Workflow 是否跟随模板更新

候选方案：

- 始终跟随模板最新版本。
- 提醒用户一键升级并自动合并。
- 创建后完全脱钩，只记录来源。

结论：首期完全脱钩。

原因：Workflow Node ID、变量引用、用户修改、已发布 Revision 和在途 Run 共同决定真实执行语义。自动同步或合并会引入难以解释的图合并和运行风险。来源记录足以支持分析；未来若做升级，应作为独立的差异预览与显式迁移产品。

### 第五轮：模板如何生产、是否需要另一套后台

候选方案：

- 直接修改数据库 JSON。
- 在代码中维护常量或 Seed。
- 从现有 Workflow Draft 执行「转换为模板」，再由模板管理入口完成元数据、检查和发布。
- 首期开放所有租户投稿。

结论：选择现有 Workflow 编辑器上的「转换为模板」功能，不建设第二套模板编辑器。

原因：模板仍需要独立的版本、发布治理和资源脱敏边界，但画布、节点定义、配置面板、布局和校验没有必要复制。转换器只负责 Draft 快照复制、租户资源清理和配置项生成，新增节点只维护一次；租户能否执行该动作由模板发布权限控制，首期不开放普通租户投稿到公共模板。

## 14. MVP 验收标准

- 用户可在 Workflow 列表下方看到推荐模板区块，点击「查看更多」后在弹窗内分页浏览模板。
- 关闭模板弹窗或返回详情上一级后，Workflow 列表的筛选、分页和滚动位置保持不变。
- 模板列表无 N+1 请求，分页、筛选和稳定排序由数据源完成。
- 用户可在详情中查看完整图、分支和节点配置摘要，任何交互都不能修改模板。
- 同一应用请求无论重试多少次只创建一个 Workflow。
- 应用只生成 Draft，不生成 Revision，不提交审核，不启用。
- 应用后的 Draft 能正常保存、编辑、校验、提交审核、发布和启用。
- 模板中的租户资源全部为空，配置清单能定位到对应节点。
- 模板下线或发布新版本不会改变已经应用的 Workflow。
- placeholder、draft-ready、不兼容或含租户数据的模板无法发布。
- 模板浏览、应用、配置完成、审核、发布和首次运行漏斗可以按 Template Version 归因。

## 15. 已确认决策

以下决策已确认，可直接进入技术拆解和交互稿：

1. 模板采用 Workflow 列表下方区块，全部模板通过「查看更多」弹窗分页浏览，不新增一级模板页面。
2. 模板详情在浏览弹窗内完成只读查看，不跳转独立详情路由。
3. 模板内容通过现有 Workflow 编辑器中的「转换为模板」生成，不建设第二套模板画布。
4. 转换读取当前 Workflow 的最新已保存 Draft，不要求 Workflow 从未发布。
5. 「应用模板」一键创建可编辑 Draft，不直接发布或启用。
6. 应用后的 Workflow 与模板脱钩，只保留模板 ID、版本和配置清单快照。
7. 首期只有全平台公共模板，不做企业私有模板和租户投稿。
8. `workflow_template_manage` 采用后端写死的 `uid + sub_user_id` 白名单，不使用环境变量；MVP 一个权限覆盖转换、元数据、检查、发布、下线和归档。
9. 同一权限用户通过自动检查后可直接发布，不引入双人审批。
10. 租户资源全部通过配置项显式选择，不自动按名称匹配；无法识别的租户资源字段阻断转换。
