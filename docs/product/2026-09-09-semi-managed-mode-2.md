# 半托管模式 2.0

日期：2026-09-09

状态：产品方案。核心规则已在产品讨论中确认；下文标注的首版交互建议用于产品与研发评审，不表示已经实现。

## 1. 产品定位

半托管模式 2.0 从“为客户消息生成推荐回复”升级为“AI 基于会话协助客服处理业务”。

AI 负责理解需求、匹配能力、执行获准的查询，并提出回复或操作建议；客服负责确认业务操作和对客发送。客服确认启动 SOP 后，SOP 按自身流程自动运行，内部节点不再逐次要求授权。

核心原则：**入口固定、能力可扩展、AI 负责匹配、人负责关键决策。**

## 2. 背景与问题

目前半托管围绕消息生成推荐回复，并将结果展示在对应消息下方。这种以最终回复为中心的交互，难以承载业务处理：

- 客服需要知道 AI 查了什么、查到了什么，不能只看到最终话术。
- 订单绑定、退款等写操作需要明确确认和结果回显，不能隐藏在生成回复过程中。
- 一次处理可能跨越查询、业务操作、启动 SOP 和回复起草，不是一条消息对应一份答案。
- 技能数量增长不应使客服承担选择技能、工具或 SOP 的复杂度。

参考视频借鉴的是“内部处理记录、当前建议、对客草稿分离”的交互。写操作授权和 SOP 整体授权是本项目明确的产品规则，不是从视频推断的行为。

## 3. 已确认的核心规则

1. AI 可以自动匹配并按照适用技能处理会话，不需要客服先选择或批准技能。
2. 已授权、无业务写入且符合自动执行策略的查询，可以直接执行。
3. AI 直接发起的退款、绑定等写操作，必须先形成操作建议，由客服确认。
4. 半托管生成的对客回复草稿，必须由客服确认发送。
5. 启动 SOP 必须人工确认；确认即整体授权该次 SOP 运行，包括流程内的写操作与消息发送，内部节点不再要求人工授权。
6. 客户新消息、首次打开新会话，以及客服主动唤起，使用一致的能力匹配和执行策略。
7. 客服通过 composer 的 `/ → AI 操作建议` 主动请求最新建议，不通过 `/售后技能` 等命令选择底层能力。
8. 忽略建议只收起当前建议，不禁用 AI；主动唤起应基于最新上下文重新判断，而不只是恢复旧卡片。

## 4. 产品概念与能力模型

### 4.1 四类资源的职责

| 资源 | 职责 | 例子 |
| --- | --- | --- |
| 技能 | 描述某类问题的适用场景、处理规则和资源使用方式 | 售后处理：识别订单、查政策、判断可采取的动作 |
| 工具 | 完成具体的数据查询或业务操作 | 查询订单、关联订单、申请退款 |
| 知识库 | 提供业务事实、政策和回答依据 | 商品资料、退换货条件、服务说明 |
| SOP | 按预定义步骤、分支和等待条件执行流程 | 售后跟进、回访流程 |

技能不是需要整体批准的黑盒。AI 按技能推进时，每个具体动作仍受执行策略约束。SOP 与技能不同：人工确认启动 SOP 后，该次流程按整体授权执行。

### 4.2 四类业务能力

| 能力 | 客服需要完成的事 | 主要资源 | 产出 |
| --- | --- | --- | --- |
| 查找与分析 | 查订单、查政策、理解当前问题 | 技能、知识库、只读工具 | 内部参考结果 |
| 起草与改写 | 生成回复、缩短、调整表达 | 技能、知识库、会话上下文 | 待发送草稿 |
| 办理业务 | 绑定订单、退款、更新业务资料 | 工具及技能中的处理规则 | 执行结果 |
| 启动流程 | 让客户进入指定业务流程 | SOP | 流程运行记录和进度 |

这些分类用于解释和配置能力，不要求在客服菜单中逐项暴露所有资源。

### 4.3 两种建议与自动执行活动

| 对象 | 定义 | 示例 |
| --- | --- | --- |
| 回复建议 | 建议生成或采用的对客回复，发送需要客服确认 | 根据物流结果向客户解释进度 |
| 操作建议 | 需要客服授权的具体业务动作 | 将订单关联到当前客户、退款、启动售后 SOP |
| 自动执行活动 | AI 已获准自行执行的分析或查询过程，不是待确认建议 | 正在查询订单、已查询到物流信息 |

建议类型稳定为“回复”和“操作”；查询中、待确认、执行中、成功、失败等属于状态，不新增建议类型。工具和 SOP 是操作建议的不同执行目标，不分别增加顶层建议类型。

自动执行活动产生内部结果；内部结果不是对客消息，也不是待执行的操作建议。

## 5. 执行与授权规则

### 5.1 半托管动作策略

| 策略 | 适用场景 | 行为 |
| --- | --- | --- |
| 自动执行 | 获准的知识检索、订单查询等 | AI 按需执行并展示必要结果 |
| 人工确认 | 直接业务写入、启动 SOP、发送回复草稿 | 展示具体建议，确认后执行 |
| 禁止执行 | 无权限、资源不可用或平台禁止的动作 | 不执行，不能通过确认绕过限制 |

执行策略由平台与客户配置定义，由执行端校验，不能由模型自行判断“无害”后放行。只读是自动执行的重要依据，但敏感信息查询、收费调用等仍可能需要确认或禁止。

首版边界：AI 直接业务写入保持人工确认，不开放通过客户配置将其静默改为自动执行。启动已配置 SOP 的整体授权是单独且明确的规则。

### 5.2 确认必须具体

操作建议至少让客服知道：准备做什么、作用于哪个客户或业务对象、关键参数是什么。例如订单、退款金额、退款原因。

- 缺少必要参数时先补齐，不能让客服确认一个不明确的动作。
- 授权绑定具体动作和参数；关键参数变化必须重新确认。
- 运行技能、请求建议、生成草稿，都不构成对后续写操作的授权。
- 关闭卡片或忽略建议，不代表取消已提交的操作，也不会撤销已完成的业务变更。

### 5.3 SOP 整体授权

启动建议应展示 SOP 名称、目标客户、启动参数和关键执行范围，尤其说明流程会自动执行其中的业务操作或发送消息。

客服确认后：

- 启动该次 SOP 运行，内部节点不再弹出半托管确认。
- SOP 内部发送不进入半托管草稿确认流程。
- 展示运行进度和结果；“已启动”不等于“全部完成”。
- 关闭会话窗口、忽略其他建议，不会因此停止 SOP。
- 整体授权不绕过 SOP 自身的权限、可用性、业务校验或失败处理规则。
- 授权不扩展到 SOP 之外的新动作，也不意味着后续可以任意重复启动。

SOP 停止、版本变化和失败恢复沿用或对齐现有 SOP 运行规则，不在本产品文档中另设一套机制。

## 6. 统一处理链路

```text
客户新消息 / 首次打开新会话 / 主动请求 AI 操作建议
  → 获取最新会话上下文及已有处理状态
  → 判断需求，匹配适用技能、知识库、工具和 SOP
  → 按需自动执行获准的分析与查询
  → 展示内部结果
  → 形成回复建议、操作建议，或判断无需建议
  → 人工确认具体操作后执行
  → 根据真实结果继续判断并更新建议
```

自动与主动触发使用相同标准，差异仅在触发来源。没有适用技能时不强行进入某个技能；信息不足时可以建议向客户补充询问，不编造业务参数。

建议不要求每轮固定产生一条回复和一条操作。可以只有一种、存在多条候选，或没有建议。存在依赖时先处理前置动作，例如退款成功前不能提供宣称退款成功的可发送回复。

## 7. 工作台交互

本节为首版交互建议，核心授权边界遵循第 3、5 节。

### 7.1 会话区：展示处理事实

客户和客服消息保留原有职责；AI 处理过程和结果以明确的内部记录展示，客户不可见，也不进入对客发送内容。

- 查询活动显示简要进度和业务结果，可按需展开。
- 写操作显示对象、关键参数、执行状态和结果。
- SOP 显示启动结果、运行状态及查看流程详情的入口，复用既有运行详情能力。
- 展示业务结果与可核实依据，不展示模型内部思维过程或原始接口日志。
- 内部记录独立于回复草稿存在，不能因忽略建议或删除草稿而消失。

### 7.2 AI 辅助条：突出当前决策

位于 composer 附近，展示当前主要建议，其他候选按需展开，避免占据大量消息区空间。

| 情况 | 展示与操作 |
| --- | --- |
| 正在分析或查询 | 简要活动状态，不要求确认 |
| 有回复建议 | 生成或查看草稿、忽略 |
| 有操作建议 | 查看对象与参数、确认执行、忽略 |
| 正在执行 | 进度，避免重复提交 |
| 执行失败 | 明确失败结果，按动作安全性提供后续处理 |
| 无操作建议 | 主动请求时反馈“暂无操作建议”；自动判断时无需反复提示 |

### 7.3 Composer：草稿与固定入口

回复草稿在输入区附近呈现，客服可以采用、编辑、发送或忽略。AI 不得覆盖客服正在编辑的内容。

`/` 菜单保持少量目的型入口：

| 入口 | 含义 | 规则 |
| --- | --- | --- |
| AI 操作建议 | 请 AI 基于当前会话判断下一步 | 重新进入统一处理链路，不直接授权业务写入 |
| 生成回复 | 请 AI 起草当前应回复的内容 | 必要时可以执行获准查询；遇到写操作依赖仍须确认 |
| 改写功能 | 缩短、调整语气、翻译等 | 仅在存在草稿时提供，具体项后续交互评审确定 |

不默认提供 `/售后技能`、工具清单或全部 SOP 清单。即使配置了 100 个技能，也由 AI 匹配适用能力，客服不承担判断底层资源的责任。

### 7.4 忽略、新消息与会话切换

- 忽略后收起当前建议，同一上下文不持续重复弹出。
- `/ → AI 操作建议` 根据最新上下文重新判断；仍有效的结果可以复用，不为重新显示建议强制重做查询。
- 客户新消息触发更新；已有建议需要重新校验，不盲目执行基于旧信息的动作。
- 重开已有会话恢复处理状态，根据上下文是否变化决定是否重新判断，不因重复打开而重复执行。
- 切换会话时隔离建议、草稿和活动记录，不能串到另一个客户。
- 新消息不隐式取消已经提交的操作或已启动 SOP；应结合其实际状态给出后续建议。
- SOP 已在运行时，应识别其处理状态，避免重复启动相同业务流程或产生与其当前处理冲突的建议。

## 8. 典型场景

### 8.1 售后查询与退款

1. 客户询问售后，会话中已提供订单号。
2. AI 匹配售后技能，提取订单号，自动调用获准的订单查询工具。
3. 会话区显示查询结果，AI 结合售后政策形成退款操作建议。
4. 客服检查订单、金额和原因，确认退款。
5. 执行端校验并执行，回显实际结果。
6. AI 基于结果起草回复，客服确认发送。

退款失败或结果未知时，不能生成“退款成功”的确定性回复；也不能因为重新生成建议而重复退款。

### 8.2 忽略后主动唤起

1. AI 提出订单关联建议，客服暂时忽略。
2. 客服在 composer 输入 `/`，选择“AI 操作建议”。
3. AI 重新判断当前上下文；如果订单仍未关联且建议有效，重新给出建议。
4. 如果客服已经通过其他入口完成关联，则不再建议重复关联，转而判断下一步。

### 8.3 启动售后 SOP

1. AI 完成必要查询，建议启动适用的售后跟进 SOP。
2. 客服查看目标客户、启动参数以及流程自动处理范围，确认启动。
3. SOP 按配置执行内部节点，业务写入和消息发送不再要求客服确认。
4. 工作台回显运行状态，客服可查看执行详情。

### 8.4 没有合适操作

客户只是表达感谢，或当前没有可办理事项。AI 不因存在售后技能就调用它；主动请求时可以反馈无操作建议，必要时仅提供适当的回复建议。

## 9. 扩展与客户定制

对客服保持固定入口，通过后台资源和能力配置适配客户，不为每个客户定制一套菜单。

| 定制需求 | 扩展方式 |
| --- | --- |
| 商品资料、业务政策不同 | 配置知识库 |
| 处理经验、匹配条件、回复风格不同 | 配置技能及其资源引用 |
| 订单、CRM 等业务系统不同 | 接入工具，定义输入、结果、权限和执行策略 |
| 跟进步骤、等待条件和分支不同 | 配置 SOP |
| Agent 服务范围不同 | 配置允许使用的技能、工具、知识库与 SOP |

建议为可调用能力提供一致的描述：名称、适用场景、输入要求、执行目标、结果含义、权限与执行策略。复用现有技能、工具和 SOP 资产，不另建一套平行编排系统。

管理员决定可用资源和执行边界；AI 在这些边界内匹配能力；客服只判断业务建议。客户配置不能突破平台限制或当前客服的权限范围。

新增普通工具或 SOP 应复用建议、确认、执行结果的通用交互；确有特殊业务信息时再扩展专用结果展示，不要求每接入一个能力就改工作台主流程。

## 10. 对技术设计的约束

本节描述必须满足的产品语义，不预设接口、数据库结构或消息传输协议。

- 区分建议、具体动作、执行结果与回复草稿，不能只扩展推荐正文来承载所有状态。
- 自动触发和主动触发进入同一套匹配与执行规则。
- 权限和确认要求在执行端强制校验，隐藏按钮或提示词不能替代授权控制。
- 确认绑定动作、对象和关键参数；提交时检查建议是否仍有效。
- 执行状态不能仅依赖前端卡片，需支持会话重开和请求中断后的恢复。
- 重复点击、网络重试、重新生成建议不得重复业务写入或重复启动 SOP。
- 超时或断线不能直接等同于执行失败；结果未知时先核实，不能提供无条件重试写操作。
- 查询和操作结果以实际服务响应为依据，不以模型生成的“成功”作为执行事实。
- 多客服操作同一会话时，需防止同一建议被重复执行，并反映业务状态已变化的情况。
- SOP 启动接入现有运行体系，整体授权不变成对其他半托管动作的全局授权。

## 11. 首版范围与非目标

首版主链路建议聚焦：固定入口、能力自动匹配、获准查询、操作确认、SOP 整体授权、内部结果展示，以及回复草稿确认发送。

本次不要求：

- 建设供客服浏览和选择全部技能、工具、SOP 的命令市场。
- 新建独立的技能编排或 SOP 引擎。
- 对所有工具设计独立页面或表单；优先使用通用交互。
- 展示完整技术调用日志或模型思维过程。
- 将直接业务写入开放为模型自行授权的自动操作。

## 12. 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 首次打开新会话或收到客户新消息 | 基于当前上下文分析并更新建议，不强制产生操作 |
| 已提供订单号且匹配售后技能 | 获准的订单查询自动执行，无需选择技能或确认查询 |
| AI 判断需要直接退款 | 展示具体退款建议，确认前不调用退款执行接口 |
| 退款参数在确认后发生变化 | 不沿用旧授权执行，要求重新确认 |
| 退款成功但客服删除回复草稿 | 退款结果保留，删除草稿不撤销退款 |
| 查询失败或写操作结果未知 | 不虚构成功，不盲目重试写操作 |
| 忽略建议后主动唤起 | 基于最新状态重新判断，不仅恢复旧建议 |
| 配置大量技能 | 客服菜单仍保持固定入口，AI 负责匹配 |
| 客户没有售后需求 | 不强行执行售后技能 |
| 确认启动 SOP | 整体授权该次运行，内部写入和发送不再次要求确认 |
| 重复点击或重复打开会话 | 不重复业务写入或启动同一已提交的 SOP 操作 |
| 切换会话、新消息到达 | 不串会话、不覆盖人工草稿，旧建议重新校验 |
| 当前客服无执行权限 | AI 和确认操作均不能绕过权限 |

## 13. 后续对齐项

核心产品语义已确认，无需再等待 SOP 授权方式决策。进入详细设计时需对齐以下实现与交互范围：

- 单聊与群聊的首版覆盖范围；现有群聊仅手动触发的行为不能默认为本次一并改变。
- 辅助条多建议排序、草稿展开方式与改写菜单的具体交互。
- 首批接入技能、查询工具、写操作工具和可启动 SOP 清单。
- 现有生成服务、工具执行服务和 SOP 启动能力的接入边界及所需契约。
- 上下文更新、查询结果有效性、重复操作识别与正在运行 SOP 的协调规则。

上述事项应在技术设计或交互稿中收敛，不改变“直接写操作人工确认、SOP 启动整体授权”的核心边界。
