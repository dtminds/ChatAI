# AI 积分计费实施计划

目标：先完成客户侧计费认知，再完成 Node 用量采集，最后与 Java Billing 联调。商业规则以[计费方案](../product/monetization/2026-09-09-ai-credit-billing-alignment.md)为准；内测免费覆盖全部能力，不追溯扣费。

## 阶段一：计费说明与入口

目的：先让客户知道相关能力如何计费，但不接真实用量、不扣费；订阅页现有占位内容保持不变。

- [x] 模型接口补充 `credit_multiplier`；使用整数基点表达倍率（`100 = 1x`、`150 = 1.5x`、`200 = 2x`），前端统一换算并展示。
- [x] Agent 与 Workflow 复用同一公共模型选择器和模型 DTO，在每个模型选项右侧展示倍率。
- [x] 抽取公共计费标识，在 Agent、会话洞察、用户记忆配置及 Workflow AI 节点展示；配置页面不展开具体积分。
- [x] 所有计费标识统一跳转订阅页；订阅页保留现有内容并增加“计费说明”入口。
- [x] 新增独立计费说明页，统一说明计费公式、基础积分、模型倍率和各能力计费单位。
- [x] 抽取共享的计费展示配置，避免页面散落基础积分和文案；展示配置不承担正式计价职责。

验收：四类能力入口可达、文案和价格口径一致、模型倍率说明清楚；订阅页除新增计费说明入口外保持现有内容。

## 阶段二：Node 用量采集与 Outbox

目的：在 Java 接口 ready 前，准确生产可上报的业务级 Usage Event。此阶段不依赖 Java、不开放真实账单。

- [ ] 核对现有回复、洞察、记忆、Workflow 完成边界、模型标识及 Workflow 节点执行实例标识。
- [x] 在 `@chatai/contracts` 定义 Usage Event、批量上报、逐条确认、账单汇总和明细查询协议；倍率使用整数基点，账单积分使用六位小数字符串。
- [x] 在 `@chatai/llm` 提供业务级 Usage Event 校验与构造入口，不绑定底层单次模型调用。
- [x] 提供 Node `xy_wap_embed_ai_usage_outbox` 的最终 DDL、唯一约束、索引、事务写入、租约恢复和投递状态流转。
- [x] 会话洞察按逻辑会话生成一次业务事件；摘要、打标、质检内部 Token 汇总，自动更新和内部重试不重复计费；主动重刷使用新业务键。
- [x] 用户记忆按成功的 run item 生成事件；成功但无记忆变更仍计量，跳过和失败不收费。
- [ ] Workflow 按成功的节点执行实例生成事件；未执行分支不计量，循环每次执行分别计量，内部重试不重复计量。
- [x] 保留实际模型、输入 Token、输出 Token 和业务对象快照；Node 不计算正式积分。
- [ ] 实现 outbox 后台批量 HTTP 投递器：有界批次、有限并发、租约恢复、退避和原事件键补发；接口未就绪时默认关闭。
- [ ] 用模拟 Java 服务验证 accepted、duplicates、rejected、超时、部分失败和重复投递；模拟结果不能标记生产事件已送达。

验收：业务结果与 outbox 持久化一致；事件幂等键稳定；失败可恢复；AI 主流程不因计费投递失败而重试或失败；三类 Node 事件可回放。

## 阶段三：Java Billing 联调

目的：接入 Java 统一账单服务，生成内测 Shadow 账单。

- [ ] Java 实现 `ai_usage_bill` 及索引，按事件键幂等接收并保存用量、基础积分、模型倍率、价格版本、应计/减免/实扣积分。
- [ ] Java 接入 AI 回复计量；Java 内部写入回复 Usage Event，不通过 Node 回调。
- [ ] Java 提供批量接收和账单查询接口，逐条返回接收、重复、拒绝结果。
- [ ] Node 接通真实批量接口；Backend 通过 Java 查询接口提供订阅页数据，不直接访问 Java 数据库。
- [ ] 订阅页展示真实 Shadow 账单：应计积分、内测减免、实扣积分为 0，并按能力、模型和账期汇总。
- [ ] 对齐免费期按业务发生时间生效，延迟上报不追溯扣费；验证价格快照和历史账单稳定性。

验收：四类能力均能从真实链路产生账单；重复上报不重复记账；Java 暂时不可用时 Node 事件可补发；订阅页账单与 Java 明细一致。

## 本计划不包含

- 正式余额预占、扣减、退款和额度拦截
- Node 直接写 Java 账单表或依赖 Java 数据库
- 将 Java、Node 的大模型调用统一迁移到同一服务
- 在 Node 侧复制一套正式积分计算器

## 验证要求

每阶段按受影响路径执行定向测试和 CI 对齐 build，覆盖业务去重、主动重跑、循环、多轮、失败、租约恢复、混合模型、免费期延迟投递和价格快照；最终执行 `git diff --check` 并审阅完整改动。真实 Java 事务和幂等能力只能在阶段三联调验证，不能由模拟测试替代。
