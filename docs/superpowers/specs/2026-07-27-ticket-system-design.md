# 智能待办升级工单系统设计方案

- 日期：2026-07-27
- 状态：已确认，待实现
- 适用范围：聊天工作台、工单中心、会话洞察、Insights Worker、共享契约与数据库
- 目标入口：`/chat/tickets`
- 关联方案：
  - [会话洞察底座设计](./2026-06-01-conversation-insights-design.md)
  - [会话洞察页面设计](./2026-06-01-conversation-insights-page-design.md)
  - [会话基础数据持续生成与会话洞察分层需求](../../specs/insights-always-on-sessionization.md)

本文是“智能待办升级为工单系统”的当前有效设计。与上述旧文档中的“待处理页”“行动项只影响洞察模块”等约定冲突时，以本文为准。旧文档保留为历史设计记录，本期不回改旧文档。

## 1. 需求结论

现有由会话洞察生成的“智能待办”升级为租户级工单系统。工单既可由正常自动 Final 洞察生成，也可由客服在单聊聊天窗口中人工创建；工单拥有独立的负责人、状态、优先级、截止时间、操作记录和评论。

工单是独立业务域，不再从属于会话洞察：

1. 人工工单不要求必须关联逻辑会话或消息。
2. 逻辑会话可为工单提供接待上下文，但不是工单创建前置条件。
3. 工单创建不得触发、唤醒、等待或补跑 Sessionization 任务。
4. 会话洞察关闭后，人工工单及已有工单仍可正常使用。
5. `todo_enabled` 的产品名称统一调整为“智能创建工单”，只控制正常自动 Final 洞察是否创建 AI 工单。
6. 所有人工重刷，包括全部、QA 和分类重刷，均不得创建工单。

## 2. 背景

现有 `xy_wap_embed_session_action_item` 已支持 AI 和人工来源，但产品形态仍是会话洞察中的轻量“待办”：

- 只能围绕逻辑会话使用。
- 没有明确负责人和领取/分配流程。
- 没有处理中、取消、明确截止时间等完整状态。
- 缺少统一工单中心、评论和操作记录。
- 接口、路由和页面均位于 Insights 域内。

逻辑会话现已从会话洞察开关中解耦，可以作为工单的可选上下文。工单本身仍应独立存在，避免因切片延迟、无对应接待会话或线下沟通场景阻塞客服记录和处理事项。

## 3. 目标与非目标

### 3.1 产品目标

1. 客服可在单聊聊天窗口中快速创建工单。
2. AI 可从正常自动 Final 洞察中创建工单。
3. 工单可被领取、分配、处理、完成和取消，并保留完整操作记录。
4. 工单可选关联接待会话；切片延迟时可使用消息锚点提供上下文。
5. 提供独立工单中心，支持客服个人、接待范围和管理员全局视图。
6. 聊天窗口只查看当前聊天的历史工单。
7. 保持会话洞察详情中原有待办区域的布局和快捷处理体验。

### 3.2 非目标

第一期不包含：

- 群聊客户工单。
- 从工单中心或会话洞察详情新建工单。
- 人工选择单条消息作为创建交互。
- 为工单触发或加速逻辑会话切片。
- 消息锚点自动升级为逻辑会话关联。
- 创建后修改工单关联上下文。
- 附件、子工单、SLA、审批流。
- 独立通知中心、站外通知或复杂订阅规则。
- 因账号接管关系变化而批量刷新历史工单字段。

## 4. 术语与领域边界

| 产品术语 | 内部含义 | 说明 |
| --- | --- | --- |
| 聊天窗口 | `xy_wap_embed_conversation` | 工单所属的单聊窗口和接待账号；不是证据上下文 |
| 接待会话 | `xy_wap_embed_logical_session` | 由连续消息形成的逻辑会话；对客统一称“接待会话” |
| 当前会话 | 创建表单中的虚拟选项 | 保存时由服务端根据聊天窗口最新消息时间和最近接待会话覆盖边界解析，不等同于客户端预先传入的 `session_id` |
| 关联消息 | `anchor_message_id` | 切片延迟时用于回看前后消息的锚点 |
| 所属账号 | 聊天窗口对应的接待账号 | 由 `conversation_id` 动态解析，不随接管关系变化回写 |
| 负责人 | `assignee_sub_user_id` | 负责处理工单的子账号，可为空 |

产品界面不得使用“平台会话”描述上下文。聊天窗口天然存在，只有“是否关联某个接待会话”需要用户选择。

## 5. 创建入口与表单

### 5.1 入口

人工创建仅支持单聊聊天窗口：

- 在聊天窗口右上角现有“更多”按钮左侧新增工单图标按钮。
- 图标按钮提供明确的可访问名称和 Tooltip“创建工单”。
- 群聊窗口不展示该入口。
- 工单中心不提供“新建工单”按钮。
- 会话洞察详情不提供新建入口。

### 5.2 创建表单

创建弹窗至少包含：

| 字段 | 必填 | 默认值 | 规则 |
| --- | --- | --- | --- |
| 标题 | 是 | 空 | 去除首尾空白后 1-120 个字符 |
| 描述 | 否 | 空 | 补充背景和处理要求，最多 2000 个字符；新建和编辑时显示实时字数 |
| 优先级 | 是 | 中 | 低、中、高 |
| 截止时间 | 否 | 空 | 使用明确时间 `due_at`，不使用文案判断逾期 |
| 负责人 | 否 | 当前创建人 | 可选创建人、其他有所属账号访问权的子账号或未分配 |
| 关联接待会话 | 是 | 当前会话 | 选项为当前会话、历史接待会话、不关联 |

这里“关联接待会话”字段必须有明确选项，但“不关联”是合法值，因此工单上下文本身可为空。

### 5.3 历史接待会话选项

服务端查询属于当前 `conversation_id` 的最近 5 个逻辑会话，按最近结束时间和会话 ID 倒序。若第一条已被识别为“当前会话”，则从历史选项中移除，避免与固定的“当前会话”选项重复；其余选项至少展示接待时间范围和可用摘要，没有摘要时只展示时间范围。

历史接待会话一次返回，不提供分页、游标或“加载更多”交互，也不允许选择更早的逻辑会话。

服务端必须校验提交的历史 `session_id`：

- `uid` 与当前租户一致。
- `conversation_id` 与创建工单的聊天窗口一致。
- 当前操作者具有该聊天窗口访问权限。

校验失败时拒绝创建，不得静默改绑到其他上下文。

## 6. 上下文解析规则

### 6.1 固定数据关系

- `conversation_id` 必填，表示工单所属聊天窗口及所属接待账号。
- `session_id` 可空，表示明确关联的接待会话。
- `anchor_message_id` 可空，表示切片延迟时的消息锚点。
- `session_id` 与 `anchor_message_id` 在新建工单时最多写入一个。
- 创建成功后不允许修改 `conversation_id`、`session_id` 或 `anchor_message_id`。

### 6.2 选择“当前会话”

保存时由服务端执行一次轻量解析：

1. 读取聊天窗口的 `last_msgtime` 与 `last_audit_info_id`。
2. 查询该聊天窗口最近 1 个逻辑会话；上下文选项接口可一次查询最近 5 个，但“当前会话”只判断第一条。
3. 取 `coverage_ended_at = next_close_at ?? ended_at`。只要 `last_msgtime` 非空、覆盖边界非空且 `last_msgtime <= coverage_ended_at`，该最新逻辑会话就是当前会话，写入其 `session_id`。
4. 上述条件不成立时，认为最新消息尚未被现有逻辑会话覆盖，写入聊天窗口的 `last_audit_info_id` 作为 `anchor_message_id`。
5. 聊天窗口没有消息锚点时，`session_id` 和 `anchor_message_id` 均为空，仍允许创建工单。

该判断不要求逻辑会话仍为 `open`。例如客户最后一条消息发生在数日前，最新逻辑会话虽已关闭，但只要聊天窗口此后没有新消息，`last_msgtime <= ended_at`，它仍是创建工单时的“当前会话”。反之，若聊天窗口已有发生在上一会话覆盖边界之后的新消息，则保存最新审计消息 ID 作为降级锚点，等待详情按锚点展示上下文。

Tickets 不扫描原始审计消息、不批量查询 `logical_session_message` 归属，也不复制切片侧的消息有效性规则。解析发生并发变化时，以创建请求当次重新读取的聊天窗口和最近逻辑会话为准；消息锚点已能提供稳定降级，不增加重试、锁或补偿任务。

### 6.3 选择“历史接待会话”

服务端校验所选接待会话后直接写入 `session_id`，`anchor_message_id = NULL`。

### 6.4 选择“不关联”

服务端写入 `session_id = NULL`、`anchor_message_id = NULL`。这用于线下、电话或其他渠道已完成沟通，仅需在当前客户名下记录工单的场景。

### 6.5 上下文展示

工单详情按以下优先级展示上下文：

1. 有 `session_id`：展示该接待会话内的消息。
2. 无 `session_id`、有 `anchor_message_id`：在同一 `conversation_id` 内展示锚点前 10 条和后 10 条消息，并标明锚点消息。
3. 两者均无：显示“未关联接待会话”，不影响其他工单操作。

消息上下文必须继续执行现有聊天访问权限校验。用户可以因“分配给我”或“我创建的”看到工单本身，但如果已失去所属账号访问权，则不得读取聊天消息和接待会话内容。

### 6.6 与切片系统解耦

人工创建工单时明确禁止：

- 创建或唤醒 `sessionize_uid` 任务。
- 修改任何 Sessionization 水位或租约。
- 等待 UID Worker 追平。
- 新增轻量补切任务。
- 后台自动将 `anchor_message_id` 替换为 `session_id`。

## 7. 工单模型

### 7.1 核心字段

第一期复用物理表 `xy_wap_embed_session_action_item`，避免无业务价值的整表改名；代码模块、共享契约和公开 API 统一收敛到独立 `tickets` 领域。

主要字段语义如下：

| 字段 | 规则 |
| --- | --- |
| `id` | 工单主键，第一期直接显示为工单编号 |
| `uid` | 租户隔离键 |
| `conversation_id` | 必填，工单所属聊天窗口 |
| `session_id` | 改为可空，关联接待会话 |
| `anchor_message_id` | 新增，可空，消息上下文锚点 |
| `snapshot_id` | AI 工单对应的 Final 洞察快照；人工工单为空 |
| `source_type` | 沿用 `ai` / `manual`；前端显示“智能创建”/“人工创建” |
| `title` | 工单标题 |
| `description` | 新增，可空，工单描述 |
| `priority` | `low` / `medium` / `high` |
| `assignee_sub_user_id` | 新增，可空，负责人子账号 |
| `due_at` | 新增，可空，明确截止时间 |
| `due_hint` | 保留为 AI 原始时效提示，不参与逾期计算 |
| `status` | 工单状态，见 7.2 |
| 创建、更新、完成、取消信息 | 记录对应操作者和时间；取消人使用 `canceled_by_sub_user_id` |

`action_type` 第一阶段保留物理字段以兼容现表，所有人工和 AI 工单固定写入 `follow_up`；该字段不作为工单中心的用户可配置分类，也不继续扩展旧行动项类型体系。

### 7.2 状态

第一期状态固定为：

| 产品状态 | 存储值 | 说明 |
| --- | --- | --- |
| 待处理 | `open` | 已创建，尚未开始处理 |
| 处理中 | `in_progress` | 已明确开始处理 |
| 已完成 | `done` | 已完成处理 |
| 已取消 | `canceled` | 不再处理，不允许物理删除 |

逾期是派生标签，不是状态：

```text
due_at < DB 当前时间
AND status IN ('open', 'in_progress')
=> overdue = true
```

允许的主要流转：

```text
open -> in_progress / done / canceled
in_progress -> open / done / canceled
done -> open
canceled -> open
```

领取未分配工单时，只原子写入当前子账号为负责人，不读取、不限制也不修改原状态。客服需要通过独立的“开始处理”操作将 `open` 工单改为 `in_progress`。已经被他人领取时返回冲突，不覆盖现有负责人。

进入 `done` 时写入当前 `completed_at` 和 `completed_by_sub_user_id`，进入 `canceled` 时写入当前 `canceled_at` 和 `canceled_by_sub_user_id`。从终态重新打开时清空主表对应终态字段；历次完成、取消和重新打开仍完整保留在 `ticket_activity`。状态变化不自动清空负责人。

`in_progress` 必须始终存在负责人：

- 工单进入 `in_progress` 时，`assignee_sub_user_id` 必须已有值或在同一请求中被赋值。
- 清空 `in_progress` 工单负责人时，必须在同一原子更新中将状态退回 `open`。
- 不允许持久化 `status = in_progress AND assignee_sub_user_id IS NULL` 的组合。

### 7.3 旧状态兼容

发布时通过数据库变更统一旧值：

- `open` 保持不变。
- `done` 保持不变。
- `dismissed` 迁移为 `canceled`。
- `expired` 迁移为 `canceled`，避免无明确 `due_at` 的历史失效事项重新进入待处理数量。

新代码不得再写入 `dismissed` 或 `expired`。原 `dismissed_at` 在数据库变更中重命名为 `canceled_at`，保留已有时间数据；迁移后的 `dismissed` / `expired` 如无取消时间，则使用原 `update_time` 填充 `canceled_at`。历史取消人无法可靠还原，`canceled_by_sub_user_id` 保持为空。

### 7.4 不删除

工单不提供删除 API 或删除按钮。误建、不再处理或重复工单统一进入“已取消”，并写入操作记录。

## 8. 负责人、所属账号与接管关系

### 8.1 所属账号

所属接待账号由 `conversation_id` 对应聊天窗口的 `third_userid` 确定，不新增一份随接管变化更新的所属账号字段。

### 8.2 负责人

负责人关联子账号 `assignee_sub_user_id`，不是接待账号：

- 人工创建默认负责人为创建人。
- 创建人可改选当前有所属账号访问权的其他子账号。
- 创建人可选择“未分配”。
- AI 创建时读取生成当时所属接待账号的 `host_sub_id`；没有有效接管人时保持未分配。
- 负责人候选始终只包含当前有所属接待账号访问权的子账号。

“待领取”是无有效接管人、人工主动选择未分配或负责人被人工清空时的兜底队列，不追求与“分配给我”相同的工单量。第一期不因此把 AI 工单默认负责人改为未分配。

### 8.3 接管变化

接管关系变化不得回写已有工单：

- 不修改历史工单负责人。
- 不反复刷新历史工单字段。
- 不自动把未分配工单指派给新接管人。
- 只影响“我接待的”的实时查询范围和后续 AI 工单的默认负责人；负责人候选仍由账号访问权决定。

如果既有负责人之后失去所属账号访问权，工单负责人保持不变。该负责人仍可查看和处理工单自身，但聊天消息上下文继续按当前会话权限决定是否可见。

## 9. 权限规则

### 9.1 可见范围

普通客服可查看以下工单的并集：

- `assignee_sub_user_id` 为本人。
- `created_by_sub_user_id` 为本人。
- 所属接待账号当前在本人可访问范围内。

管理员和 Owner 除上述范围外，还可以查看租户全部工单。

所有查询必须先按 `uid` 隔离。工单本身的可见权限和消息上下文权限分别判断，不能因为工单可见而绕过聊天访问权限。

### 9.2 操作权限

普通客服的工单写权限统一按以下主体关系判断，不因入口位于工单中心、聊天窗口或洞察详情而变化：

| 当前用户与工单的关系 | 改标题/描述/优先级/截止时间 | 改状态 | 改负责人 | 添加备注 |
| --- | --- | --- | --- | --- |
| 负责人是自己 | 允许 | 允许 | 允许 | 允许 |
| 人工工单由自己创建且当前未分配 | 允许 | 允许 | 允许 | 允许 |
| 人工工单由自己创建但已分给他人 | 允许 | 允许 | 允许 | 允许 |
| 仅因所属账号访问权可见 | 不允许 | 不允许 | 不允许；未分配时只能领取给自己 | 不允许 |
| 洞察详情中看到 AI 工单 | 按上述主体关系判断 | 按上述主体关系判断 | 按上述主体关系判断 | 按上述主体关系判断 |
| 管理员 / Owner | 允许 | 允许 | 允许 | 允许 |

具体规则：

1. 普通客服只要是当前负责人或该人工工单的创建人，即拥有该工单的编辑、状态、备注和重新分配权限。
2. 仅因所属账号访问权而看到工单的普通客服只有读取权限；工单未分配时，可以通过“领取”原子指派给自己，领取成功后获得负责人权限。
3. 重新分配的目标必须是当前对所属接待账号有访问权的子账号，也可以清空为未分配。
4. 管理员和 Owner 可编辑租户内全部工单，但新负责人仍必须满足所属账号访问约束。
5. `POST /tickets/:ticketId/comments` 与“可修改该工单”使用完全相同的权限，不单独放宽。
6. 聊天窗口创建要求操作者具有当前聊天访问权；管理员和 Owner 也不绕过聊天访问校验。
7. 洞察详情的“完成 / 忽略 / 重新打开”就是 Tickets 状态写操作。无 Tickets 写权限时只展示状态，不提供可操作控件。
8. 未分配 AI 工单通常没有人工创建人。普通客服在洞察详情中仅因账号范围可见时不能直接完成或忽略；点击标题进入工单详情领取后，才获得负责人写权限。洞察详情不为此新增领取入口。

后端是权限权威来源，不能只依赖前端隐藏视图或按钮。

## 10. 工单中心

### 10.1 路由与导航

工单作为独立一级模块，入口为：

```text
/chat/tickets
/chat/tickets/:ticketId
```

工单中心只负责查询、领取、分配和处理，不提供创建入口。

### 10.2 固定视图

| 视图 | 查询口径 | 可见角色 |
| --- | --- | --- |
| 我的待办 | 负责人为当前子账号，且状态为待处理或处理中 | 所有人 |
| 分配给我 | 负责人为当前子账号 | 所有人 |
| 我接待的 | 当前由该子账号接管（账号 `host_sub_id` 为当前子账号）的全部工单，不限制负责人 | 所有人 |
| 我创建的 | 人工创建人是当前子账号 | 所有人 |
| 待领取 | 当前子账号有访问权的账号下负责人为空的工单 | 所有人 |
| 全部工单 | 当前租户全部工单 | 仅管理员和 Owner |

管理员或 Owner 同时作为接待客服时，仍可使用“我接待的”查看自己当前接管账号的工单；“全部工单”才表示跨账号的租户全局视图。账号被其他子账号重新接管后，会动态移出原接管人的“我接待的”，但工单负责人字段不发生变化。

### 10.3 筛选与搜索

支持以下筛选：

- 状态。
- 所属账号。
- 负责人。
- 来源：人工创建、智能创建。
- 优先级。
- 截止时间：逾期、今日、未来 7 天、无截止时间。
- 创建时间范围。

支持按工单编号和标题搜索。

筛选只能收窄当前视图的权限范围，不能通过参数扩展用户可见范围。“全部工单”参数对普通客服返回无权限，不得退化成隐式全量查询。

### 10.4 默认排序

默认排序优先级固定为：

1. 已逾期且未结束。
2. 今日到期且未结束。
3. 高优先级。
4. 最近更新时间。

同一优先级下使用 `id DESC` 保证稳定翻页。

上述优先级允许第一期在数据库查询中使用 `CASE WHEN` 表达式排序，并接受过滤后的小范围 filesort；不得为覆盖该表达式盲目堆叠组合索引。排序必须在数据库分页前完成，不能只对单页结果进行应用层重排。实现后以真实查询 `EXPLAIN` 和慢查询监控决定是否需要派生排序字段。

### 10.5 列表与详情

列表至少展示：

- 工单编号、标题。
- 客户名称、所属账号。
- 状态、优先级、来源。
- 负责人。
- 截止时间和逾期标签。
- 创建人、创建时间、更新时间。

详情至少展示：

- 标题、描述和全部工单属性。
- 关联接待会话或消息锚点上下文。
- AI 工单的洞察来源和证据消息。
- 操作记录和评论时间线；最新记录在上，首屏只加载最新一页，可继续加载更早记录。
- 状态、负责人、优先级、截止时间编辑操作。

### 10.6 数量

第一期只提供以下数量，不建设独立通知中心：

- 一级“工单”导航：当前用户“我的待办”的数量，即负责人为当前子账号且状态为 `open + in_progress`。
- “待领取”视图：当前有访问权的账号范围内 `assignee_sub_user_id IS NULL AND status = open` 的数量。
- 聊天侧：只统计当前 `conversation_id` 下 `open + in_progress` 的工单数量。

## 11. 聊天窗口工单区

### 11.1 展示范围

聊天窗口右侧工单区域只展示当前 `conversation_id` 下的工单，不提供“该客户全部工单”或其他跨聊天窗口范围。前端和公开 API 均不得接收客户标识或范围参数；服务端始终以路径中的当前聊天 ID 作为唯一查询范围，并继续执行单聊和访问权限校验。

### 11.2 快捷处理

聊天侧支持：

- 打开工单详情。
- 领取未分配工单。
- 更新状态。
- 查看负责人、优先级和截止时间。

复杂编辑和完整操作记录在工单详情中完成，聊天侧保持紧凑。

## 12. 智能创建工单

### 12.1 开关

保留数据库字段 `todo_enabled`，但所有产品文案统一改为“智能创建工单”。该开关：

- 只控制 AI 自动创建工单。
- 不影响人工创建。
- 不隐藏或清理已有工单。
- 不控制工单中心权限。
- 不控制逻辑会话生成。

### 12.2 唯一允许的生成路径

只有正常自动 Final 分析同时满足以下条件时才允许创建 AI 工单：

```text
analysis mode = final
AND 本次任务来自会话正常结束后的自动分析
AND todo_enabled = 1
```

以下路径一律不得创建工单：

- Live 分析。
- 全部维度人工重刷。
- QA 人工重刷。
- 分类人工重刷。
- 任何其它 `manual_reanalyze` 路径。

人工重刷可以更新洞察快照，但不能新增、替换、取消或重新打开工单。

### 12.3 AI 工单字段

AI 工单写入：

- `conversation_id`：逻辑会话所属聊天窗口。
- `session_id`：本次 Final 分析对应逻辑会话。
- `snapshot_id`：本次 Final 快照。
- `anchor_message_id = NULL`。
- `source_type = ai`。
- `action_type = follow_up`。
- `assignee_sub_user_id`：生成时所属账号有效的 `host_sub_id`，不存在则为空。
- 标题、优先级、`due_hint` 和证据：沿用模型输出及现有校验。

AI 工单保留 `session_id + snapshot_id + evidence` 的证据链，证据 `dimension_type` 第一阶段固定沿用 `action_item`。`due_hint` 不自动等价为 `due_at`；只有后续具备可靠的绝对时间转换规则时才写入明确截止时间。

### 12.4 去重与数量保护

保留现有会话窗口级保护：

- 读取当前 `conversation_id` 最近 10 条工单标题，归一化后去重。
- 活跃工单数超过 5 条时抑制本轮 AI 工单生成。

状态升级后，活跃工单定义为 `status IN ('open', 'in_progress')`。人工与 AI 工单均计入保护范围，避免 AI 无视客服已创建的同类事项继续生成。

## 13. 会话洞察兼容

### 13.1 移除旧“待处理”页面

从会话洞察二级导航移除“待处理”，并删除旧页面路由：

```text
/chat/insights/follow-ups
```

旧地址不做跳转、不保留兼容页，访问时按未注册路由处理。代码中的旧导航项、页面组件和只为该页面服务的数据请求应一并移除。

原有入口按业务语义调整：

- “待跟进事项”类指标跳转 `/chat/tickets?source=ai&status=open,in_progress`。
- 高风险会话跳转洞察分析明细并携带风险筛选，不把风险记录伪装成工单。

### 13.2 洞察详情中的工单区域

洞察详情原“待办任务”区域的布局、呈现和快捷操作保持不变，不新增创建入口。唯一新增交互是：点击工单标题，在新窗口打开 `/chat/tickets/:ticketId`。

数据范围固定为：

```text
source_type = ai
AND snapshot_id = 当前详情展示的洞察快照 ID
```

不得仅按相同 `session_id` 查询，否则会把人工工单或其他快照生成的工单混入当前洞察详情。

原快捷操作继续提供“完成、忽略、重新打开”：

- `open` 或 `in_progress`：提供完成和忽略；完成写入 `done`，忽略写入 `canceled`。
- `done` 或 `canceled`：提供重新打开，底层写入 `open`。
- 完成、忽略和重新打开均保留当前负责人，不因状态变化自动清空 `assignee_sub_user_id`。
- 洞察详情可继续使用“忽略”的原交互文案。
- 未分配且当前用户仅因所属账号访问权可见的 AI 工单只展示状态；用户可点击标题进入工单详情领取，洞察详情不新增领取按钮。

状态操作统一调用 Tickets 领域服务，不再由 Insights Repository 维护另一套状态逻辑。

### 13.3 旧接口

新前端切换后移除以下旧业务接口，不做别名或转发：

```text
GET   /api/server/insights/follow-ups
POST  /api/server/insights/action-items
PATCH /api/server/insights/action-items/:actionItemId/status
```

会话洞察详情读取可继续在 Insights 响应中返回限定范围内的工单投影，但写操作必须使用统一 Tickets API。

## 14. API 设计

共享 DTO 放入 `@chatai/contracts` 的 Tickets 领域。公开 Tickets 契约中的 ID 沿用现有 Insights 契约的 `string` 序列化，不做额外 MySQL `BIGINT` 精度重构。

### 14.1 创建与上下文选项

```text
GET  /api/server/tickets/context-options?conversationId={id}
POST /api/server/tickets
```

创建请求建议：

```json
{
  "conversationId": "123",
  "title": "跟进退款到账情况",
  "description": "客户希望明天下午前确认",
  "priority": "high",
  "dueAt": "2026-07-28T10:00:00.000+08:00",
  "assigneeSubUserId": "456",
  "context": {
    "type": "current"
  }
}
```

`context.type` 支持：

```text
current
session + sessionId
none
```

服务端不能接收客户端直接指定 `anchor_message_id`；该字段仅由“当前会话”解析产生。

`context-options` 不接收历史接待会话分页参数；服务端固定返回当前聊天窗口最近 5 个逻辑会话。

### 14.2 列表、详情与计数

```text
GET /api/server/tickets
GET /api/server/tickets/counts
GET /api/server/tickets/by-conversation/:conversationId
GET /api/server/tickets/:ticketId
GET /api/server/tickets/:ticketId/activities?beforeActivityId=<id>&pageSize=20
```

列表查询包含 `view`、分页、排序和 10.3 节筛选字段。所有范围由服务端根据 JWT 中的 `uid`、`subUserId`、角色和账号访问关系计算。

处理记录按 `activity.id DESC` 稳定排序。默认每页返回最新 20 条；加载更早记录时使用 `beforeActivityId` 游标查询 `id < beforeActivityId`，不得使用 `OFFSET`。新评论使用评论接口返回的真实 activity 直接插入列表顶部。

### 14.3 更新与领取

```text
PATCH /api/server/tickets/:ticketId
POST  /api/server/tickets/:ticketId/claim
POST  /api/server/tickets/:ticketId/comments
```

`PATCH` 只允许修改：

- 标题。
- 描述。
- 负责人。
- 优先级。
- 截止时间。
- 状态。

上下文字段出现在更新请求时直接拒绝。领取接口使用条件更新保证同一工单只能被一个人成功领取。

`PATCH` 语义固定为：

- 普通字段采用后写覆盖。
- 请求包含 `status` 时必须同时提交 `expectedStatus`。
- 状态更新使用 `WHERE status = expectedStatus` 条件写入；条件不匹配返回 `TICKET_STATE_CONFLICT`，由前端刷新最新工单。
- 领取继续使用独立条件更新，不通过普通 `PATCH` 模拟。
- `PATCH` 清空 `in_progress` 工单负责人时必须原子写入 `status = open`；尝试把无负责人工单改为 `in_progress` 时返回 `INVALID_TICKET_STATUS_TRANSITION`。

评论去除首尾空白后必须非空，最大 2000 个字符。

### 14.4 主要错误码

| 错误码 | 场景 |
| --- | --- |
| `TICKET_NOT_FOUND` | 工单不存在或不在当前租户 |
| `TICKET_FORBIDDEN` | 无查看或操作权限 |
| `TICKET_SINGLE_CHAT_ONLY` | 尝试在群聊创建工单 |
| `INVALID_TICKET_CONTEXT` | 所选接待会话不属于当前聊天窗口 |
| `INVALID_TICKET_ASSIGNEE` | 负责人不具备所属账号访问权 |
| `TICKET_ALREADY_CLAIMED` | 待领取工单已被他人领取 |
| `INVALID_TICKET_STATUS_TRANSITION` | 状态流转不允许 |
| `TICKET_STATE_CONFLICT` | 工单状态已被其他操作更新 |

## 15. 数据库设计

### 15.1 现表扩展

`xy_wap_embed_session_action_item` 至少完成以下变更：

```text
session_id               BIGINT UNSIGNED NULL
anchor_message_id        BIGINT UNSIGNED NULL
description              TEXT NULL
assignee_sub_user_id     BIGINT UNSIGNED NULL
due_at                   DATETIME NULL
status                   支持 open / in_progress / done / canceled
dismissed_at             重命名为 canceled_at
canceled_by_sub_user_id  BIGINT UNSIGNED NULL
```

建议索引按实际查询补充：

```text
(uid, assignee_sub_user_id, status, update_time, id)
(uid, conversation_id, status, update_time, id)
(uid, status, due_at, priority, update_time, id)
(uid, created_by_sub_user_id, update_time, id)
(uid, source_type, status, update_time, id)
```

索引以工单中心最终 SQL 和 `EXPLAIN` 为准，避免为所有筛选组合建立组合索引。客户全量工单通过当前 `conversation_id` 解析 `uid + platform + third_external_userid`，并结合可见聊天范围查询；第一期不在工单表冗余客户标识。

### 15.2 工单活动表

新增轻量活动表承载操作记录和评论，建议命名：

```text
xy_wap_embed_ticket_activity
- id
- uid
- ticket_id
- activity_type
- operator_type: sub_user / ai / system
- operator_sub_user_id NULL
- content NULL
- detail_json NULL
- create_time
```

`activity_type` 第一阶段支持：

```text
created
comment_added
status_changed
assignee_changed
priority_changed
due_at_changed
content_updated
```

评论使用 `comment_added + content`；字段变更使用 `detail_json` 保存必要的 before/after，不保存无法展示的大对象快照。

工单创建和首条 `created` 活动、工单更新和对应活动必须分别在同一数据库事务中提交。这里引入事务是为了保证用户可见的操作历史不缺失；任一写入失败时整个操作失败并允许用户重试，不设计异步补偿状态机。

### 15.3 写入边界

两张表均需加入 Node 后端可写白名单。消息审计表、聊天窗口表和逻辑会话表继续只读；工单系统不得为补充上下文修改平台层数据。

## 16. 异常与边界

1. **切片延迟**：保存消息锚点，工单立即创建。
2. **没有消息**：无上下文创建，不报错。
3. **聊天已失效**：创建时要求聊天仍有效且操作者有访问权；既有工单仍保留。
4. **接管变化**：不回写负责人，只改变动态查询和后续默认值。
5. **负责人失去账号权限**：保留负责人；消息上下文按当前权限隐藏。
6. **并发领取**：仅一个条件更新成功，其他请求返回 `TICKET_ALREADY_CLAIMED`。
7. **并发修改**：第一期采用后写覆盖普通可编辑字段；状态和领取仍校验当前值，不增加复杂版本状态机。
8. **AI 重复标题**：最近 10 条标题去重；重复项不写入。
9. **AI 活跃工单过多**：超过保护阈值时本轮不创建 AI 工单，不影响洞察其他结果。
10. **人工重刷**：无论选择哪些分析范围，均不创建工单。
11. **上下文读取失败**：工单详情仍可展示，消息区域单独显示无权限或加载失败。
12. **旧地址访问**：`/chat/insights/follow-ups` 不跳转，按未注册路由处理。

## 17. 实施边界与顺序

建议按以下依赖顺序实施，但可以在同一版本发布：

1. 数据库字段、状态迁移、活动表和 Kysely 类型。
2. Tickets 共享契约、Repository、Service、权限和 API。
3. 工单中心列表、详情、视图和筛选。
4. 聊天窗口创建入口、创建弹窗和聊天侧工单区。
5. Insights Worker 的 AI 工单写入迁移到 Tickets 领域，并补齐 Final/重刷边界。
6. 洞察详情改用工单服务，标题增加新窗口链接。
7. 删除旧“待处理”导航、路由、页面和旧 Insights 写接口。

发布必须保证新 Tickets 读写链路先可用，再切换洞察详情和 Worker，最后删除旧页面及接口；不需要为旧前端地址提供跳转兼容。

## 18. 验收标准

### 18.1 人工创建

1. 单聊窗口右上角可打开创建弹窗，群聊不展示入口。
2. 工单中心和洞察详情均无创建入口。
3. 默认选择“当前会话”；最近接待会话的 `next_close_at ?? ended_at` 覆盖聊天窗口 `last_msgtime` 时保存 `session_id`，不要求会话仍为 `open`。
4. 最新消息发生在最近接待会话覆盖边界之后时保存 `last_audit_info_id` 为 `anchor_message_id`。
5. 无消息锚点、选择“不关联”时均可成功创建无上下文工单。
6. 可明确选择历史接待会话，跨聊天窗口的 `session_id` 被拒绝。
7. 创建动作不产生或唤醒任何 Sessionization 任务。
8. 创建后不能修改聊天窗口、接待会话或消息锚点。
9. 当前会话解析不扫描审计消息或消息归属表，不触发切片。
10. 接待会话固定查询最近 5 个；识别为当前会话的第一条从历史选项移除，不提供分页或更早会话选择。

### 18.2 工单处理

1. 支持待处理、处理中、已完成、已取消及规定的重新打开流转。
2. 逾期由 `due_at` 和当前时间派生，不写 `expired` 状态。
3. 未分配工单并发领取时只有一个请求成功。
4. 标题、描述、负责人、优先级、截止时间和状态可按权限修改。
5. 不提供删除能力；取消和重新打开均有操作记录。
6. 评论和关键字段变化在详情时间线中可追溯。
7. 状态更新携带 `expectedStatus`；并发状态变化时返回冲突并刷新，不静默覆盖。
8. 历史 `expired` 迁为 `canceled`，不进入未完成角标。
9. 清空处理中工单负责人会原子退回待处理，数据库中不存在未分配的 `in_progress` 工单。

### 18.3 视图与权限

1. “我的待办”“分配给我”“我接待的”“我创建的”“待领取”口径符合第 10.2 节。
2. 只有管理员和 Owner 能看到并查询“全部工单”。
3. 管理员同时能独立使用“我接待的”，不会被强制导向全局范围。
4. 接管关系变化只改变动态范围，不修改既有工单负责人。
5. 工单可见但无聊天权限时，工单内容可见、消息上下文不可见。
6. 负责人和人工创建人具有写权限；仅因所属账号访问权可见的客服只能读取或领取未分配工单。
7. 聊天侧接口只查询路径指定的当前 `conversation_id`，不接受跨聊天窗口范围参数。

### 18.4 AI 创建

1. `todo_enabled` 在产品中统一显示为“智能创建工单”。
2. 正常自动 Final 且开关开启时可创建 AI 工单。
3. Live 分析不创建工单。
4. 全部、QA、分类等所有人工重刷均不创建工单。
5. AI 工单保留 `session_id + snapshot_id + evidence`。
6. 最近 10 条标题去重和活跃工单数量保护继续有效。
7. AI 创建时负责人取当时有效 `host_sub_id`，接管变化不回写。
8. `todo_enabled = 0` 时，提示词不请求行动项且持久化层不写入 AI 工单。

### 18.5 会话洞察兼容

1. 会话洞察导航不再出现“待处理”。
2. `/chat/insights/follow-ups` 路由已删除且不跳转。
3. 洞察详情工单区域的布局、展示和完成/忽略/重新打开快捷操作保持不变。
4. 洞察详情只展示当前快照生成的 AI 工单，不混入人工工单。
5. 点击工单标题在新窗口打开工单详情。
6. 洞察详情的状态写入统一走 Tickets 服务。
7. `in_progress` 工单可完成或忽略，终态工单可重新打开，操作始终服从 Tickets 写权限。
8. 未分配 AI 工单对仅因所属账号访问权可见的客服保持只读，可通过标题进入详情领取；洞察详情不新增领取入口。

## 19. 已确认决策

以下事项不再作为开发阶段开放问题：

1. 第一期仅支持单聊客户。
2. 人工创建入口仅在聊天窗口。
3. 负责人关联子账号，所属账号由聊天窗口确定。
4. 接管关系变化不刷新历史工单。
5. 关联上下文可为空，且创建后不可修改。
6. 最新消息不在最近接待会话覆盖边界内时使用 `last_audit_info_id` 作为锚点，不触发切片。
7. 不提供选择单条消息的创建交互。
8. 工单中心视图名称使用“我接待的”和“全部工单”，两者口径不同。
9. 会话洞察详情保持原有工单交互，仅增加标题跳转。
10. 所有人工重刷均不创建工单。
11. 旧“待处理”地址直接移除，不做跳转。
